# 设计说明（决策点）

改结构前读这一页；规矩（怎么写 / 怎么判）在技能 `SKILL.md`。

## 0 边界与目标

目标：把散落的单据与自述变成可检索、可追溯、可带走的档案；人只负责扔单据 + 确认。
不做：不诊断、不给用药建议、不判断紧急度、不补造数据。只做搬运、结构化、检索 —— 输出一旦「解释病情」就会被当医疗意见，代价由用户承担。

## 1 六条主线（按视角切，不按科室 / 病种）

| 主线 | 载体 | 回答 |
|---|---|---|
| 感受 | `3-不适记录` | 什么时候有过什么不舒服 |
| 事件 | `4-就医记录` + `2-检查报告` | 看了什么病、结果、用了什么药 |
| 药物 | `6-用药` | 吃了多久、调过几次、为什么停 |
| 数值 | `5-指标` | 某指标这几年的走势 |
| 体态 | `8-体重管理` | 体重 / 体成分怎么变的 |
| 血糖 | `10-血糖数据` | 一次监测期里血糖怎么随进食起伏 |

- 不按科室分：同一份数据被多个科室用到（一次血常规同时服务内分泌与消化），按科室必然重复；视角彼此正交，各线自成一体。
- 指标单独成 CSV：报告是事件快照，指标是时间序列；趋势必须跨事件聚合，散在各页只能全文搜。
- 体重单列：口径不同（有报告的临床数值 vs 自测值、无参考范围）、频率不同（一年几次 vs 一天几次）、用途不同（给医生 vs 自己看曲线）。代价：跨表曲线（体重 + 肝功）要合并两个文件，真需要时写脚本。
- 药品库存单列：库存答「家里还有什么、何时过期、治什么」，流水答「谁在吃、吃多久」；变化方式不同（状态 vs 追加事件）→ 用 `状态` 列 + 不删行。两表不联动：精细扣减是持续动作、成本落在人身上；而「就医记录 × 用药流水」的交叉是一次性事实，两处都写没有增量成本。
- 血糖单列且只存文件：一次监测期七千多个点、AGP 报告十几张图，拆成行会造出一张比 `5-指标` 大两个数量级的表，而这些点只有配着事件簿（吃了什么）才读得懂 —— 单看一串数字没有意义。原始文件 + 事件标签就是它的「可检索形态」，真要算 delta 时再写脚本。

## 2 库 → 人 → 档案 与编号 1–10

- 成员层一开始就留好（健康档案天生多人），事后迁移更贵。
- 编号 = 阅读顺序；数字前缀让排序稳定（拼音 / 字母序会漂）。
- 共享内容（`8-知识库/` 词表、技能 `templates/`）只有一份：复制就会分叉。
- 曾用过跳号（`00-/10-/15-/90-` 这类），实际不需要中间插目录 → 改顺号，不重排、不跳号。
- 同号不同层：成员级 `8-体重管理/`、`9-药品管理/`、`10-血糖数据/` 与库级 `8-知识库/`、技能 `templates/`，引用带路径。

## 3 一次检查活动 = 一个目录；汇总页 + 单报告页并存

- 目录是唯一能「打包带走」的单位（zip 给医生 / 换电脑）—— 原图与报告必须在一起。
- 汇总页 = 合并视图（给人回看）；单报告页 = 拆分视图（供聚合检索），也是图像型 / 描述型报告（心电图、CT、超声、内镜）的唯一文字载体。
- ≤7 天合并：一周内的几张单子通常就是同一次看病开的检查。
- 活动日期取最早：活动是事件起点，取最早才能按时间排序并与就医记录那一行对齐。
- 各单据自己的日期不改写：活动是合并视图；单据日期被统一改写会毁掉「近 N 次」时间线。
- ≥8 天默认不合并：跨度更大更像复诊或独立事件。
- 必须问、不能自动判：7 天只是信号不是证据；判错的代价是两个事件被并成一个，而就医记录只增不改。

## 4 原图命名 `YYYY-MM-DD_〈标准名〉_原图[_pN].ext`

文件名是 Markdown 里唯一能承载结构化元数据的地方 → 命名固定才能一条命令取全「近 10 次心电图原图」。代价：归档时必须 rename。一单据多项目用 `+` 连接，任一项目名都能捞到同一张图。

## 5 受控词表是地基

同义异写（心电图 / ECG / 心电检查）会让任何自动统计漏项。新项目：先问用户 → 定标准名 → 补词表（含别名）。

## 6 ID 列配对

Markdown 表格行挂不了块 ID → 用 `ID`（`YYYYMMDD+序号`）↔ 活动页 frontmatter `就医ID` 双向配对，也可用于对账漏链。

## 7 只增不改 / 派生例外 / 基准线 / git

- 只增不改：医疗记录篡改历史比留错字危险；下游视图与报告都建立在源数据上。订正 = 追加 + 标注。
- 例外只有 `7-视图/`：投影必须反映最新上游，源数据不动，丢了可再生成。
- `1-基本信息/` 基准线只读：数字每次都有细微差别，「要不要同步」的追问是纯开销；差异不是冲突，是不同时间的两次记录。
- 每次归档 commit：本地 git = 后悔药 + 审计，无远程、不上云。

## 8 就医记录 × 用药流水 有意交叉

本列 = 本次开药（事件快照，反查一眼看到）；流水 = 药物一生（吃多久、调几次、为什么停）。取舍：查单次就诊的频率远高于核对一致性 → 接受重复，规定两处都写，只更新一处算待核对。

## 9 不适记录只有四列、不打卡

加字段会抬高填写成本，而它最大的敌人是人懒得写；照原话录（改写会丢掉本人的描述精度）。不做依从性记录 —— 没人愿意用的记录系统等于没有。与「自查」并存不覆盖：自查 = 自己判断 + 自己吃药（一次医疗接触）。

## 10 通用名（剂型）+ 药库做成 SQLite

- 商品名会变、会重复；通用名才是身份。
- 精确匹配，不做向量检索：药名错一个字就是另一个药，语义检索在这里是风险。
- 不记频次：回忆不准，只会产生 `[信息缺失]` 噪声；用药记录不是依从性台账。
- SQLite + 脚本查询：说明书库上万条、每条数千字，塞上下文既贵又慢；默认截断，要原文加 `--full`。
- 许可：公开整理集多有版权问题 → 仅个人自用、不再分发；本仓库不附带任何药品数据。

## 11 面向医生的报告：脱敏 + PDF

报告要带出门交给外人 → 只放 性别 / 年龄段 / 身高体重 / 过敏史 / 慢病 / 用药 / 指标；不放全名 / 身份证 / 电话 / 住址 / 单位。医生场景是打印翻阅存档，不是渲染 Markdown → PDF。四段结构按门诊问诊顺序排。

## 12 会话是投递窗口

按单据类型自动分发，用户不必纠结放哪个会话；带图片的会话要短（图片每轮重发）；归档完成后会话删 / 归档不影响库（数据在磁盘）。

## 13 视觉标记（emoji）的分层

emoji 只出现在**渲染页**（汇总页 / 单报告页 / `7-视图/` 三件套），由 技能 `templates/` 固化；数据层（CSV、指标总表、就医记录总表、frontmatter）不加 —— 渲染页供人扫读定位，数据层保持可解析、无噪声。

## 14 已知取舍与待办

| 项 | 说明 |
|---|---|
| 项目名仍需人工确认 | 词表是地基，宁可多问一句 |
| 原图归档依赖 rename 纪律 | 靠规律而非工具；出错靠 git 回溯 |
| 7 天阈值仍需人工确认 | 阈值只是「问一句」的触发条件，归属一律用户定 |
| 药品库无中文商品名批量源 | 商品名逐条确认，库只保证通用名 |
| 多成员视图同名 | 跳成员引用写路径链接 `[[〈成员〉/主档案]]` |
| 未实现（有意，未排期）：自动复查提醒 | `下次复查` 列已预留结构化日期，需要时接定时任务即可 |
| 未做：报告 PDF 一键生成 | 方案已定（HTML + 打印 CSS → 无头浏览器），首次出报告时落地 |
| 血糖数据无结构化总表 | 有意为之（七千多点的表读不出信息，标注已在文件里）；需要算 delta 时现写脚本 |

## 15 不可破的边界

1. 不诊断、不给用药建议、不判断紧急度；出现胸痛 / 呼吸困难 / 大出血 / 意识丧失 / 突发严重神经症状 → 先让用户就医。
2. 不补造数据：缺失 `[信息缺失]`、推断 `[推断]` + 依据、拿不准 `[待核对]` + 留空。
3. 保留不确定性。

## 库内不放说明文件

- **库 = 数据 + 一份给 agent 读的东西（铭牌 `AGENTS.md`）**。各目录的「放什么 / 怎么记 / 边界」不在库里，收在技能 `references/vault-dirs/`：干到哪个目录就读哪一份。
- 用药的索引与来源在技能 `knowledge/用药/`；本机的备份、定时器、Obsidian 运行细节属于使用者自己的部署，不在本仓库。
- 理由：说明文件在库里会随库一起被复制、被外部 agent 当指令读，且技能一改就过期（本轮就出现 6 处指向已删脚本的路径）。放在技能里只有一个来源，改一次全对。
- 推论：**骨头（skeleton）不带 README** —— 空目录用 `.gitkeep` 占位，`init_vault.py` 复制时跳过占位文件。
